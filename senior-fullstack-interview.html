Senior Full Stack Engineer Interview Questions & Answers

Rate Limiting

Q: What is rate limiting and why is it important?

A: Rate limiting is a technique to control the number of requests a client can make to an API within a specific time window. It's important because it:

  • Prevents abuse and DDoS attacks
  • Ensures fair resource distribution among users
  • Protects backend systems from being overwhelmed
  • Reduces costs by controlling API consumption
  • Maintains service quality and availability

Q: Explain different rate limiting algorithms.

A: Common algorithms include:

1. Token Bucket: Tokens are added at a fixed rate. Each request consumes a token. If no tokens available, request is rejected. Allows bursts up to bucket size.
2. Leaky Bucket: Requests are added to a queue (bucket) and processed at a constant rate. If bucket overflows, requests are rejected. Smooths out traffic spikes.
3. Fixed Window: Counts requests in fixed time windows (e.g., per minute). Simple but can allow bursts at window edges.
4. Sliding Window Log: Tracks timestamp of each request. More accurate but memory-intensive.
5. Sliding Window Counter: Hybrid approach combining fixed window efficiency with sliding window accuracy.

Q: How would you implement rate limiting in a distributed system?

A: Use a centralized data store like Redis with atomic operations (INCR, EXPIRE). Implement using:

  • Redis INCR with TTL for simple counter-based limiting
  • Sorted sets for sliding window implementations
  • Lua scripts for atomic multi-step operations
  • Consider tools like Kong, Nginx, or API Gateway services
  • Implement retry logic with exponential backoff
API Design & Tricky Questions

Q: What's the difference between PUT and PATCH?

A: PUT is idempotent and replaces the entire resource with the provided data. PATCH is for partial updates, modifying only specified fields. PUT requires sending complete resource representation, while PATCH sends only changed fields.

Q: How do you handle API versioning?

A: Common strategies:

  • URI versioning: /api/v1/users, /api/v2/users
  • Header versioning: Accept: application/vnd.api+json;version=1
  • Query parameter: /api/users?version=1
  • Content negotiation: Custom media types

URI versioning is most common for simplicity and discoverability.

Q: How do you handle long-running API operations?

A: Use asynchronous patterns:

  • Return 202 Accepted with a job ID or callback URL
  • Provide a status endpoint to check operation progress
  • Use webhooks to notify when operation completes
  • Implement WebSockets for real-time progress updates
  • Use message queues (RabbitMQ, SQS) for background jobs

Q: Explain idempotency and why it matters.

A: Idempotency means making the same request multiple times produces the same result as making it once. Critical for:

  • Network retry safety
  • Preventing duplicate charges/transactions
  • GET, PUT, DELETE are naturally idempotent
  • POST is not - use idempotency keys to make it safe
  • Example: Stripe uses idempotency keys to prevent duplicate charges

Q: How do you handle pagination in APIs?

A: Multiple approaches:

Offset-based: ?page=2&limit=50 - Simple but inconsistent with live data changes
Cursor-based: ?cursor=xyz&limit=50 - Better for real-time data, more consistent
Keyset pagination: ?after_id=123&limit=50 - Efficient for large datasets

Include metadata: total_count, next_cursor, has_more, previous_cursor

Load Balancers

Q: Explain different load balancing algorithms.

A: Common algorithms:

  • Round Robin: Distributes requests evenly in sequence
  • Least Connections: Routes to server with fewest active connections
  • Weighted Round Robin: Considers server capacity/power
  • IP Hash: Routes based on client IP for session persistence
  • Least Response Time: Routes to fastest responding server
  • Random: Simple random selection

Q: What's the difference between Layer 4 and Layer 7 load balancing?

A:

Layer 4 (Transport Layer):
  • Routes based on IP address and TCP/UDP ports
  • Faster, less resource-intensive
  • No content inspection
  • Examples: AWS NLB, HAProxy in TCP mode
Layer 7 (Application Layer):
  • Routes based on HTTP headers, URLs, cookies
  • Content-aware routing decisions
  • Can modify requests/responses
  • SSL termination capability
  • Examples: AWS ALB, Nginx, Traefik

Q: How do you handle session persistence with load balancers?

A: Several approaches:

  • Sticky sessions: Route user to same server (IP hash, cookie-based)
  • Session replication: Sync session data across servers
  • Centralized session store: Redis, Memcached for shared sessions
  • JWT tokens: Stateless, no server session needed
  • Best practice: Use stateless authentication when possible

Q: How do you implement health checks?

A: Implement multiple levels:

  • Shallow check: Simple HTTP 200 response
  • Deep check: Verify database connectivity, dependencies
  • Configure appropriate intervals (e.g., every 10s)
  • Set unhealthy/healthy thresholds (e.g., 2 failures)
  • Return detailed status for monitoring
  • Graceful degradation during partial outages
API Traffic & Performance

Q: How do you handle API traffic spikes?

A: Multiple strategies:

  • Auto-scaling based on metrics (CPU, requests/sec)
  • Caching (CDN, Redis, in-memory caching)
  • Rate limiting to prevent overwhelming backend
  • Queue-based architecture for async processing
  • Circuit breakers to prevent cascading failures
  • Database read replicas for read-heavy loads
  • Connection pooling and keep-alive

Q: Explain the circuit breaker pattern.

A: Circuit breaker prevents cascading failures:

Closed state: Normal operation, requests pass through
Open state: After threshold failures, stop sending requests
Half-open state: After timeout, allow test requests

Benefits: Fast failure, prevent resource exhaustion, give services time to recover. Libraries: Hystrix, resilience4j, opossum.

Q: What caching strategies do you use?

A: Different levels of caching:

  • CDN caching: Static assets, edge locations
  • Application cache: Redis, Memcached for frequently accessed data
  • Database query cache: Materialize expensive queries
  • HTTP caching: Cache-Control, ETag headers
  • Cache invalidation strategies: TTL, write-through, write-behind
  • Cache warming for predictable traffic patterns

Q: How do you monitor and debug API performance issues?

A: Comprehensive monitoring approach:

  • Metrics: Response time, error rate, throughput, saturation
  • Logging: Structured logs with correlation IDs
  • Tracing: Distributed tracing (Jaeger, Zipkin, DataDog APM)
  • APM tools: New Relic, DataDog, Dynatrace
  • Database query profiling and slow query logs
  • Network latency analysis
  • Set up alerts for anomalies and SLO violations
Cloud Infrastructure

Q: Explain microservices vs monolith trade-offs.

A:

Microservices benefits: Independent scaling, technology flexibility, isolated failures, team autonomy
Microservices challenges: Network latency, distributed debugging, data consistency, deployment complexity
Monolith benefits: Simple deployment, easier debugging, no network overhead, ACID transactions
Monolith challenges: Scaling all or nothing, long deployment cycles, tight coupling

Start with monolith, move to microservices when team/system complexity justifies it.

Q: How do you ensure data consistency in distributed systems?

A: Multiple patterns:

  • Saga pattern: Choreography or orchestration-based transactions
  • Event sourcing: Store events, rebuild state
  • CQRS: Separate read/write models
  • 2-Phase Commit: For strong consistency (rarely used)
  • Eventual consistency: Accept temporary inconsistency
  • Idempotent operations and compensation logic

Q: What's the CAP theorem and how does it apply?

A: CAP theorem states you can only have 2 of 3:

  • Consistency: All nodes see same data
  • Availability: Every request gets response
  • Partition tolerance: System works despite network splits

In practice: Must choose P (partition tolerance), then decide between C or A. Examples: PostgreSQL (CP), Cassandra (AP), MongoDB (tunable).

Q: How do you implement a deployment strategy with zero downtime?

A: Common strategies:

  • Blue-Green: Two identical environments, switch traffic
  • Rolling deployment: Gradually replace instances
  • Canary deployment: Route small % to new version, monitor
  • Feature flags: Deploy code disabled, enable gradually
  • Database migrations: backward-compatible changes first
  • Health checks and automatic rollback on failures

Q: How do you design for high availability (99.99% uptime)?

A: Multiple layers of redundancy:

  • Multi-AZ deployment (different availability zones)
  • Multi-region for disaster recovery
  • Load balancers with health checks
  • Auto-scaling groups with min healthy instances
  • Database replication and automated failover
  • Backup and restore procedures (tested regularly)
  • Circuit breakers and graceful degradation
  • Monitoring, alerting, and runbooks for incidents

99.99% = ~52 minutes downtime/year. Requires careful planning and testing.

Q: Explain container orchestration and when to use Kubernetes.

A: Kubernetes manages containerized applications:

Features: Auto-scaling, self-healing, load balancing, rolling updates, service discovery
Use when: Multiple services, need portability, traffic varies significantly, team comfortable with complexity
Avoid when: Simple apps, small team, cost concerns, managed services sufficient (AWS ECS, App Service)

Alternatives: Docker Swarm, AWS ECS/Fargate, Google Cloud Run, Azure Container Apps

Security & Best Practices

Q: How do you secure APIs?

A: Multi-layered approach:

  • Authentication: JWT, OAuth 2.0, API keys
  • Authorization: RBAC, ABAC, scope-based access
  • HTTPS only (TLS 1.2+)
  • Rate limiting and throttling
  • Input validation and sanitization
  • CORS configuration
  • SQL injection prevention (parameterized queries)
  • XSS protection
  • CSRF tokens for state-changing operations
  • Security headers (HSTS, CSP, X-Frame-Options)
  • API gateway for centralized security

Q: Explain OAuth 2.0 flow.

A: Authorization framework with multiple grant types:

Authorization Code: Most secure for web apps (redirect-based)
Client Credentials: Machine-to-machine (service accounts)
PKCE: Enhanced security for mobile/SPA apps
Implicit (deprecated): Legacy SPA pattern

Flow: Client gets authorization code → Exchange for access token → Use token in API requests → Refresh when expired

Q: How do you handle secrets in cloud environments?

A: Never hardcode secrets:

  • Use secret managers: AWS Secrets Manager, Azure Key Vault, HashiCorp Vault
  • Environment variables injected at runtime
  • Rotate secrets regularly
  • Use IAM roles instead of API keys when possible
  • Encrypt secrets at rest and in transit
  • Audit secret access
  • Never commit secrets to version control

Q: What are the key metrics for API observability?

A: The Four Golden Signals:

  • Latency: Time to serve requests (p50, p95, p99)
  • Traffic: Requests per second, bandwidth
  • Errors: Failed requests rate, error types
  • Saturation: Resource utilization (CPU, memory, disk)

Additional: Apdex score, SLA compliance, downstream dependencies health

Database & Scaling

Q: How do you scale a database?

A: Multiple strategies:

Vertical scaling: Bigger machine (limited, expensive)
Read replicas: Offload reads to replica servers
Sharding: Partition data across multiple databases
Caching: Reduce database load with Redis/Memcached
Connection pooling: Reuse database connections
Indexing: Optimize query performance
Denormalization: Trade storage for query speed

Q: SQL vs NoSQL - when to use each?

A:

Use SQL when: ACID transactions needed, complex queries, well-defined schema, relational data
Use NoSQL when: Massive scale, flexible schema, horizontal scaling priority, simple access patterns
Document DBs (MongoDB): Hierarchical data, flexible schema
Key-Value (Redis, DynamoDB): Simple lookups, sessions, caching
Column-family (Cassandra): Time-series, write-heavy
Graph (Neo4j): Highly connected data, social networks

Q: Explain database indexing strategies.

A: Indexes speed up reads but slow writes:

  • B-tree: Default, good for equality and range queries
  • Hash: Fast equality lookups only
  • Composite: Multiple columns, order matters
  • Covering: Include all query columns
  • Partial: Index subset of rows (with WHERE clause)
  • Index only frequently queried columns
  • Monitor query plans and slow queries

Q: How do you handle database migrations in production?

A: Safe migration practices:

  • Version control all migrations
  • Test on production-like data volumes
  • Make backward-compatible changes
  • Add columns as nullable first, add NOT NULL later
  • Expand-contract pattern: Add new, migrate data, remove old
  • Use online schema change tools (gh-ost, pt-online-schema-change)
  • Lock-free operations when possible
  • Have rollback plan ready
Handling Millions of Requests

Q: How do you architect a system to handle millions of requests per day?

A: Multi-layer architecture approach:

1. CDN Layer: CloudFlare, CloudFront for static assets and edge caching (reduces origin requests by 70-90%)
2. Load Balancer Layer: AWS ALB/NLB, Google Cloud Load Balancer to distribute traffic across multiple regions and zones
3. Application Layer: Horizontal scaling with auto-scaling groups, containers (ECS/Kubernetes) that scale based on metrics
4. Caching Layer: Redis cluster for hot data, reduces database load by 80-95%
5. Database Layer: Primary-replica setup, read replicas for scaling reads, sharding for writes
6. Message Queue Layer: SQS, RabbitMQ, Kafka for async processing and decoupling

Q: What caching strategies reduce database load at scale?

A: Layered caching strategy:

  • L1 - Application cache: In-memory cache (node-cache, LRU cache) for ultra-hot data, millisecond latency
  • L2 - Distributed cache: Redis/Memcached cluster for shared data across instances
  • L3 - CDN cache: Edge caching for static and API responses
  • Cache-aside pattern: App checks cache first, populates on miss
  • Write-through: Write to cache and DB simultaneously
  • Write-behind: Write to cache, async persist to DB
  • TTL strategy: Short TTL (1-5 min) for dynamic data, long TTL (1-24 hrs) for static
  • Cache warming: Pre-populate cache before traffic spikes

Q: How do you prevent database overload during traffic spikes?

A: Multiple protective layers:

  • Connection pooling: Limit max connections (e.g., pgBouncer, HikariCP)
  • Query timeout: Kill long-running queries automatically
  • Read replicas: Route read traffic to replicas (5-10x capacity increase)
  • Database-level rate limiting: Throttle by user/tenant
  • Materialized views: Pre-compute expensive aggregations
  • Query result caching: Cache expensive query results in Redis
  • Graceful degradation: Serve stale cache during DB issues
  • Circuit breaker: Stop hitting DB when it's struggling

Q: How do you optimize API response times at scale?

A: Comprehensive optimization strategy:

  • Request batching: Combine multiple requests into one (GraphQL, DataLoader pattern)
  • Response compression: gzip/brotli (reduces payload by 70-90%)
  • HTTP/2: Multiplexing, header compression, server push
  • Pagination: Limit response size (cursor-based for consistency)
  • Field selection: Only return requested fields (GraphQL, sparse fieldsets)
  • Async processing: Return 202 Accepted for heavy operations
  • Database query optimization: N+1 prevention, eager loading, proper indexing
  • Keep-alive connections: Reuse TCP connections
  • Edge computing: Run logic closer to users (CloudFlare Workers, Lambda@Edge)

Q: Describe a system that handles 10 million requests per day.

A: Example architecture (10M req/day ≈ 115 req/sec average, 500-1000 req/sec peak):

Frontend: Static files on CDN (CloudFront), React/Next.js SPA
API Gateway: AWS API Gateway or Kong for rate limiting, auth, routing
Application: 10-20 Node.js/Python instances behind ALB, auto-scaling 5-50 instances
Cache: Redis cluster (3-node primary + 3 replicas), 95% cache hit rate
Database: PostgreSQL (primary + 2 read replicas), RDS with auto-scaling storage
Queue: SQS for background jobs, Lambda workers for processing
Monitoring: DataDog/CloudWatch for metrics, PagerDuty for alerts
Cost: ~$2,000-5,000/month on AWS depending on region and reserved capacity

Q: How do you handle database writes at high scale?

A: Write optimization strategies:

  • Batch writes: Collect and insert in batches (100-1000 records)
  • Async writes: Queue writes, process in background workers
  • Write-behind caching: Update cache immediately, persist later
  • Sharding: Partition data across multiple databases (by user_id, region, etc.)
  • CQRS pattern: Separate read/write databases, eventual consistency
  • Event sourcing: Append-only event log, rebuild state from events
  • Time-series databases: InfluxDB, TimescaleDB for metrics/logs
  • Optimize indexes: Fewer indexes on write-heavy tables
Frequently Asked Senior Interview Questions

Q: Explain what happens when you type a URL in a browser and press Enter.

A: Complete flow:

  1. DNS lookup: Browser → DNS resolver → Root DNS → TLD DNS → Authoritative DNS → Returns IP
  2. TCP connection: 3-way handshake (SYN, SYN-ACK, ACK)
  3. TLS handshake: Certificate verification, key exchange (if HTTPS)
  4. HTTP request: Browser sends GET request with headers
  5. Server processing: Load balancer → App server → Database/Cache → Build response
  6. HTTP response: Status code, headers, body sent back
  7. Browser rendering: HTML parsing → DOM tree → CSSOM → Render tree → Layout → Paint
  8. Resource loading: Parallel download of CSS, JS, images
  9. JavaScript execution: Parse, compile, execute

Q: Design a URL shortener like bit.ly.

A: Key components:

URL generation: Base62 encoding of auto-increment ID or hash (MD5 + collision check)
Storage: NoSQL (DynamoDB, Cassandra) - key: short_code, value: original_url + metadata
Caching: Redis for hot URLs (Pareto principle: 20% URLs = 80% traffic)
Analytics: Async write to analytics DB (clicks, referrers, geography)
Custom aliases: Check availability, reserve in separate table
Expiration: TTL on URLs, cleanup worker
Scale: 7-character code = 62^7 = 3.5 trillion URLs
Rate limiting: Prevent abuse (100 URLs/hour per user)

Q: How would you design a real-time chat application?

A: Architecture components:

  • WebSocket server: Socket.io, WS library for bidirectional communication
  • Message broker: Redis Pub/Sub or Kafka for distributing messages across servers
  • Presence system: Track online users in Redis with TTL
  • Message storage: MongoDB/PostgreSQL for history, indexed by conversation_id + timestamp
  • Push notifications: FCM/APNs for offline users
  • Read receipts: Track last_read_message_id per user
  • File uploads: S3 + presigned URLs, thumbnails via Lambda
  • Typing indicators: Broadcast via WebSocket, debounce client-side
  • Scaling: Sticky sessions or message broker routing

Q: What are common causes of memory leaks and how do you debug them?

A: Common causes:

  • Event listeners not removed (addEventListener without removeEventListener)
  • Closures holding references to large objects
  • Global variables never cleared
  • Detached DOM nodes still referenced
  • Timers/intervals not cleared (setInterval leaks)
  • Cache without eviction policy (unbounded growth)

Debugging techniques:

  • Chrome DevTools: Heap snapshots, comparison between snapshots
  • Node.js: --inspect flag, Chrome DevTools, heapdump package
  • Memory profiling over time, look for sawtooth pattern without dips
  • V8 heap profiler: clinic.js, node --heap-prof
  • Monitor in production: process.memoryUsage(), alerts on growth

Q: Explain the difference between horizontal and vertical scaling.

A:

Vertical scaling (Scale Up):
  • Add more CPU/RAM/Disk to existing server
  • Pros: Simple, no code changes, ACID transactions easier
  • Cons: Hardware limits, expensive, single point of failure, downtime during upgrade
  • Example: AWS EC2 t3.micro → t3.2xlarge
Horizontal scaling (Scale Out):
  • Add more servers to handle load
  • Pros: No limits, better fault tolerance, can scale infinitely
  • Cons: Complex, needs load balancer, stateless design required, eventual consistency
  • Example: 1 server → 10 servers behind load balancer

Best practice: Start vertical, move horizontal when needed. Databases often vertical, app servers horizontal.

Q: How do you ensure data consistency in a distributed cache?

A: Cache invalidation strategies:

  • Cache-aside with TTL: Simple but allows stale data during TTL
  • Write-through: Update cache and DB in same transaction
  • Event-driven invalidation: DB triggers → Message queue → Cache invalidation
  • Versioning: Include version in cache key, increment on update
  • Cache tags: Group related cache entries, invalidate by tag
  • Pub/Sub pattern: Broadcast invalidation to all app instances
  • Conditional requests: ETags to validate cache freshness

Trade-off: Consistency vs Performance. Choose based on business requirements (eventual consistency often acceptable).

Q: What is the N+1 query problem and how do you solve it?

A: Problem: Fetching list of items (1 query) then fetching related data for each item (N queries).

Example: Get all users (1 query), then get posts for each user (N queries) = 1 + N total queries

Solutions:

  • Eager loading: JOIN or IN query to fetch related data (1-2 queries total)
  • DataLoader pattern: Batch and cache requests (GraphQL best practice)
  • ORM settings: Sequelize: include, TypeORM: relations, Prisma: include
  • Denormalization: Store related data together (NoSQL)
  • Caching: Cache relationships in Redis

Detection: Enable query logging, count queries per request, use APM tools

Q: How do you handle file uploads at scale?

A: Best practices:

  • Direct upload: Client uploads to S3 using presigned URL (bypasses server)
  • Multipart upload: For large files (>100MB), parallel chunk uploads
  • Validation: File type (MIME), size limits, virus scanning (ClamAV)
  • Processing: Async via queue (SQS → Lambda/worker)
  • Image optimization: Generate thumbnails, convert to WebP, different sizes
  • CDN delivery: Serve from CloudFront, not origin server
  • Storage: S3 Standard → Glacier for archival, lifecycle policies
  • Progress tracking: WebSocket or polling endpoint for upload progress

Q: What is eventual consistency and when is it acceptable?

A: Eventual consistency: System guarantees all replicas will converge to same value eventually, but may be temporarily inconsistent.

Acceptable scenarios:

  • Social media likes/views count (doesn't need to be exact)
  • Product recommendations (personalization can lag)
  • Analytics dashboards (5-minute delay acceptable)
  • Search indexes (eventual freshness okay)
  • DNS propagation (TTL-based)

NOT acceptable:

  • Financial transactions (need strong consistency)
  • Inventory for purchase (avoid overselling)
  • User authentication (security critical)
  • Critical notifications

Q: Explain the difference between PUT, POST, and PATCH with examples.

A:

POST: Create new resource, non-idempotent
Example: POST /users → Creates user with server-generated ID
Calling twice creates 2 users
PUT: Replace entire resource, idempotent
Example: PUT /users/123 {name: "John", email: "john@example.com"}
Must send ALL fields, calling twice has same effect
PATCH: Partial update, can be idempotent
Example: PATCH /users/123 {email: "new@example.com"}
Only send changed fields

Best practice: Use POST for create, PATCH for updates (more efficient), PUT for full replacement
